# 3D 海岛休闲游戏逐步开发方案

**日期：** 2026-09-14  
**状态：** M0 工程基线已建立；M1 样板区实现、38项运行检查及性能测量完成，最后鼠标/贴墙手感待用户实测；M2及后续未开始，P0 尚未验收。  
**Goal：** 先完成可持续运行的第一人称海岛环境与天气里程碑，再依次建立采集建造、种田钓鱼与家园成长。  
**Architecture：** 用统一世界时钟驱动日历、太阳与天气逻辑；渲染、音频和玩法读取世界状态。天气演出与玩法规则分离，通过明确的状态查询和时间推进接口接入存档、睡眠和作物。  
**Tech Stack：** 现有 Unity 6000.0.23f1c1、HDRP 17.0.3、C#；按需要使用 Shader Graph、粒子/VFX 与 Unity Test Framework，具体可用包在 M0 核实。

## 1. 范围与确定程度

### 已确认
- 游戏名称待定，3D 海岛休闲，第一人称能看见手脚。
- 正常运行时现实 1 秒 = 游戏 60 秒，即一天现实 1440 秒（24 分钟）。
- 先地图和环境，再精细天气；P0 验收通过后进入 P1 建造。
- P0 含朝阳、晚霞、昼夜、四季、雨雪；P1 含木石、基础房屋、床、衣服、鱼竿与鱼饵。
- 后续发展种田、钓鱼、生存、家具和更多工艺。

### 规划默认值与待决事项
- 暂按 PC 单机、小团队、温带海岛组织开发；联机、移动端不纳入当前资源估算。
- 暂将 1.0 解释为“环境与天气里程碑”；不把仅天气展示视为商业完整游戏。
- 美术建议为可信光照搭配适度简化的资产；正式资产制作前确定参考和比例。
- 生存建议偏轻度；死亡惩罚、饥饿、寒冷等强度在 P2 原型中决定。
- 每季天数设为可配置，不沿用现实季度或默认照搬其他游戏。
- 一天 24 分钟包含夜晚；睡眠会跳过部分时间，P1/P2 需用实际行走和操作时长校准每日可用时间，不假设玩家有完整 24 分钟劳作。
- 首版天气不包含海面结冰、洪水、真实雪厚、雷击伤害或完整流体模拟。
- M0 确定最低测试硬件、分辨率、目标帧率；建议从 1080p/60 FPS 目标起评估，不将其当作已验证承诺。
- 不给未经团队规模、资产来源与实测支持的固定工期。每个里程碑拆成若干可独立验证的工作包后再估时。

## 2. 当前工程基线

- Unity 工程位于 `Sunset Glow/`，现有构建场景为 `Assets/OutdoorsScene.unity`。
- 场景文件中存在 Sun、Main Camera、Sky and Fog Volume、StaticLightingSky。
- 已有 `Assets/Settings/SkyandFogSettingsProfile.asset` 和 HDRP 资源；Graphics/Quality Settings 中已有管线引用。
- 本次只读文件检查找到的 C# 为 TutorialInfo 模板说明代码，未据此认定存在成熟玩法系统。
- 文件配置不等于运行结果：尚未检查编辑器控制台、场景画面、管线引用有效性或性能。

## 3. 执行顺序与开发门槛

`M0 工程基线 → M1 海岛与第一人称 → M2 时钟日历 → M3 晴天昼夜 → M4 天气 → M5 四季 → M6 P0验收 → M7 交互采集制作 → M8 建造装备 → M9 种田钓鱼生活 → M10 远期成长`

- M0—M6 属于 P0；M7—M8 属于 P1；M9 为 P2；M10 为远期。
- P0 期间允许临时小屋、材质测试板、调试操作面板，作为天气测试设施；不提前开发玩家建造玩法。
- 一个阶段完成后提交可运行构建、验证记录与已知问题，再推进后续阶段。
- 必须修复数据丢失、时间错误、崩溃、明显雨雪穿屋、严重视觉跳变和性能不达标等阻断问题；细微美术优化可以记录为后续事项。

## 4. P0 分阶段工作

### M0：工程可运行基线
**产出：** 可重复打开和构建的工程、测试配置表、基线画面与性能记录。

1. 使用工程声明版本打开 Unity，核实包恢复、Console 错误和 Graphics/Quality 的 HDRP 引用。
2. 检查当前输入配置是否可用，选定一种输入接入方式，避免混用导致控制冲突。
3. 建立独立开发场景 `Assets/_Game/Scenes/IslandPrototype.unity`，保留模板资源作为参考。
4. 确定世界单位、地理方向（建议 +Z 北、+X 东、+Y 上）、角色尺度与层/碰撞约定。
5. 固定第一台测试机器、分辨率、质量档、目标 FPS 和帧时间预算；记录 CPU/GPU/内存及构建方式。
6. 做一次桌面 Development Build，验证启动、退出、输入与画面；记录基线。

**验收：** 无阻断编译/运行错误；开发场景在构建中可进入；已有可复用的测量配置。HDRP 空场景就超预算时先解决基线问题。

### M1：海岛样板区与第一人称身体
**产出：** 可以步行探索、观察日出日落的最小海岛区域。

1. 搭海岸、浅滩、内陆缓坡、少量树木、海面和远景，不先铺满完整大地图。
2. 建立观测点：东岸、面西海岸、树林、坡顶、屋内窗边，供后续复用截图与测量。
3. 实现移动、鼠标视角、碰撞与坡面行走；处理落水边界和重置，首版不要求游泳。
4. 加入简单身体、手部待机和手脚；检查低头、贴墙、转向、头部遮挡和角色阴影。相机不直接受剧烈头部动画驱动；全身 IK 不作为 P0 必须项。
5. 设置灵敏度、视野范围、镜头晃动开关；验证暂停菜单的光标行为。
6. 放置固定测试小屋和材质测试板，测试屋顶遮蔽、木材、石头、地面和衣物材质。

**验收：** 能稳定遍历样板区，无掉出地图/明显镜头穿模；低头可见身体；海岸方向明确；测试小屋可进入。此时环境可粗糙，但必须足以检验天气。

### M2：统一时钟、日历与调试
**产出：** 可测试、可保存、可跳转的世界时间基础。

1. 用独立于画面的时钟累计游戏秒，默认倍率 60，不通过整体 `Time.timeScale=60` 加速物理和动画。
2. 定义暂停策略：单机暂停菜单暂停世界；调试加速不改变角色动作速度。
3. 定义天数、时分、季节映射及每季长度配置；只有这一处掌管时间。
4. 提供当前时间查询和时间区间推进通知；正常流逝与睡眠跳时区分，允许跨越多日，不依赖逐分钟逐日漏发的事件。正式玩法只允许向前推进；调试倒退时间需要重置快照，不用于回滚已发生的玩法结算。
5. 建调试面板：显示日期时间、暂停、倍率、指定日期/时间；调试跳转和未来正式睡眠共用受控入口。
6. 从此阶段加入最小版本化存档：世界时间与日历配置标识；验证重新加载。

**验收：** 输入现实 1/60/1440 秒分别推进游戏 1 分钟/1 小时/1 天；不同帧间隔累计结果一致；暂停不推进；跨午夜、跨季和跨多日正确；保存恢复无时间偏移。

### M3：晴天昼夜与朝阳晚霞
**产出：** 从清晨到夜晚的完整环境体验。

1. 根据世界时刻及可配置纬度/季节计算一致的太阳路径；先采用简化可信模型，不要求天文精度。
2. 驱动主光方向、强度与天空，处理太阳低于地平线后的直射光，避免夜间从地下照亮场景。
3. 联动天空散射、云层、雾、曝光和海面反射；采用运行时配置实例，避免 Play 模式修改共享源资源。
4. 加入可导航的夜间基础环境光及简单月亮/星空表现；月相系统延后。
5. 在固定观测点调清晨、正午、黄昏、夜间；日出日落窗口按太阳高度控制，不硬绑全年同一时刻。
6. 检查动态光照下的环境光、反射和室内外适应，避免静态天空/烘焙留下正午亮度。

**验收：** 正常速度连续跑完 24 分钟；日出日落方向与定义一致，春冬路径可配置；天空、地面、树木和海面明暗同步；无明显曝光闪烁、地平线穿帮或夜晚全黑。调试跳时后画面在约定适应时间内稳定。

### M4：晴、阴、雨、雪天气与环境反馈
**产出：** 可指定、可自然过渡、可恢复的四类基础天气。

1. 定义天气配置和状态：云量、降水类型/强度、风、温度参考、持续时间与过渡时间。
2. 从晴到阴、阴到雨、雨停转晴实现过渡，再加入落雪；首版使用可解释的权重和持续区间，不实现气象流体模拟。
3. 雨雪只围绕玩家渲染必要范围；风同时影响降水方向、植被和音效，不对整岛铺满粒子。
4. 加入地面湿润与渐进干燥、视觉积雪与渐进消退；按材质和表面朝向控制，避免海面、屋内和墙面无差别积雪。
5. 实现测试屋顶的雨雪遮挡、室内外声音衰减和湿润遮蔽；定义可复用遮蔽查询，P1 动态房屋复用。
6. 保存当前/目标天气、过渡进度、持续状态和随机状态（或预生成天气日程），防止读档重抽天气。时间跳跃时提供经过区间的天气摘要，后续作物不能仅用跳时终点天气计算整晚降水。

**验收：** 晴阴雨雪可重复切换，风、声音、云和地表表现协调；雨停后逐步变干；屋内无明显穿雨雪；恢复存档后天气过渡能继续；无长期粒子/音源累积。

### M5：四季环境
**产出：** 季节影响环境且与天气保持一致。

1. 配置四季的日照范围、温度区间、天气权重和环境色彩。
2. 为样板区植被建立有限季节变体，渐变或分批切换，避免午夜整岛瞬间换色。
3. 冬季提高雪出现条件，暖季不随机落雪；温度只作为简化规则，不做完整热力模拟。
4. 检查积雪增减、阴雨与日照的组合；季节长度改变必须有明确存档处理规则。
5. 调试推进完整年度，验证跨年；真实游玩仍按已确认 60 倍率运行。

**验收：** 四季可切换、可保存恢复；环境变化连续且能辨认；季节与降水组合遵循配置。作物、鱼群和服装属性此时只预留读取接口，不提前实现。

### M6：P0 集成验收与环境 1.0
**产出：** 可交付构建、验收表、画面对照、性能报告与已知问题清单。

1. 跑下方测试矩阵，处理阻断问题；保留同机同设置的前后帧时间证据。
2. 在目标硬件上分项测量水、体积云、雾、阴影、植被和雨雪，按实际瓶颈优化。
3. 至少跑两次正常速度完整昼夜（48 分钟），另做加速年度、连续天气切换和反复加载测试。
4. 在独立构建中复核输入、暂停、存档和视觉，不能只看编辑器预览。
5. 记录实际达标范围；P0 通过后将天气系统定为稳定基线，进入 P1。

**门槛：** M0—M5 验收满足；阻断缺陷清零；固定硬件/质量档性能满足约定目标；视觉在固定观测点完成检查。不是承诺任意硬件或无限场景均无问题。

## 5. P0 验证矩阵

| 维度 | 覆盖内容 | 验证方式 |
|---|---|---|
| 时间正确性 | 60 倍、暂停、不同帧间隔、跨日/季/年、多日跳时 | EditMode 纯逻辑测试 |
| 天气逻辑 | 合法季节组合、持续时间、打断过渡、固定随机状态 | EditMode 测试 |
| 保存恢复 | 晴天、雨雪中、过渡中、跨午夜、损坏或旧存档 | 往返测试与错误处理验证 |
| 渲染冒烟 | 每季 × 晴阴雨雪 × 清晨/正午/黄昏/夜间 | 调试面板遍历；不合法组合只作为强制视觉测试 |
| 重点视觉 | 晚霞转雨、冬季日出、雨雪夜晚、屋内向外看 | 固定机位截图与实际步行观察 |
| 空间遮蔽 | 海边、树林、室内、门口进出、屋檐下 | PlayMode/人工检查 |
| 稳定与性能 | 最重合法天气、连续跨日、重复加载、粒子音源数量 | 独立构建 + Profiler |

测试实现时核实 Test Framework 包和程序集配置。只对时间、状态、存档等重要逻辑写有意义的自动化测试；美术效果必须看画面，不用参数断言代替视觉验收。存档损坏应提示并保留原文件，避免自动覆盖导致不可恢复。

## 6. P1：交互、采集、制作和基础家园

### M7：物品与采集制作基础
**前置：** M6 通过。

1. 统一视线交互、距离限制、提示和动作反馈。
2. 定义稳定物品 ID、背包、堆叠、容量与存档；物品数据和场景表现分开。
3. 实现树木/石头采集、掉落和耗尽状态保存；明确资源是否刷新，避免全岛采空后卡死。
4. 实现配方与基础工作台；材料扣除和产物发放作为一次一致操作处理。
5. 打通获取木石、制作一件工具、保存退出并恢复的闭环。

**验收：** 满背包、材料不足、重复操作和读档不丢失/复制物品；资源与背包状态一致。

### M8：基础建造、床、衣物与渔具
1. 采用少量模块吸附式建造：基础、地板、墙、门、屋顶；允许旋转、取消、碰撞/坡度检查与拆除返还。
2. 验证房屋封顶后遮雨、拆屋顶后重新暴露，沿用 P0 遮蔽能力。
3. 加入床与工作台，床通过统一时间入口推进至下一个约定起床时间，而非直接改太阳角度。
4. 制作一套基础衣物、鱼竿和鱼饵，支持装备及第一人称可见外观；复杂布料模拟延后。
5. 保存建筑位置、朝向、稳定实例 ID、家具和装备；衣物/鱼竿先完成制作装备，实际钓鱼闭环在 M9。

**验收：** 从采集开始独立造出小屋并放床，过夜后日期天气正确，重进后建筑和物品保留；取消放置不扣材料，非法重叠不能建造。

## 7. P2：种田、钓鱼与轻生存

### M9：第一个完整生活循环
1. 种田先做 2—3 种作物：开垦、播种、浇水、随日历成长、收获；雨水计入浇灌。
2. 作物按经过的时间区间结算；睡眠、跨多日和加载不能跳过生长或重复收成。季节不适合作物如何处理需明确。
3. 钓鱼先做 3—5 种鱼：装备鱼饵、抛竿、等待、咬钩提示、简单收线、获得鱼；支持主动取消和异常中断。
4. 用时间、天气和钓点影响鱼种/概率，给天气观察实际价值；先不增加大量鱼种或高难度小游戏。
5. 引入体力、食物恢复和睡眠恢复；先体验轻度约束，再决定死亡、寒冷等规则。
6. 验证“看天气安排一天 → 劳作获取产物 → 改善家园 → 睡眠 → 次日新目标”的循环。

**验收：** 新存档能完成连续三天的采集/种田/钓鱼/制作/睡眠；奖励与消耗可持续；不因资源耗尽、缺必要工具或鱼饵来源断裂而卡死。

## 8. 远期扩展

### M10：家园与工艺成长
- 优先增加有明确用途的建筑、家具、储物与工具升级。
- 推荐进程：简易营地 → 自给农庄 → 木工石作 → 金属工具 → 更完善家园；名称与具体解锁再讨论。
- 每一阶段至少带来一种新的生活能力，不仅提高材料数量要求。
- 战斗、复杂武器、畜牧、NPC 社交、远航、多岛、多人联机独立评估，不默认为当前范围。
- 新内容不得破坏时间、天气与存档契约；每次扩展回归既有基础循环。

## 10. 每次开发的执行方式

1. 从当前里程碑中选一个可独立验收的小任务，写明目标、将修改的文件和验证方式。
2. 检查现状和用户未提交改动，再实施；新增资产用 Unity 正常生成并保留 `.meta`。
3. 重要纯逻辑先定义失败场景并测试；视觉任务先固定观测机位和预期效果。
4. 完成实现、必要回归和画面验证，记录实际结果，不能只写“理论上可用”。
5. 更新本文件阶段状态及 progress.md，列出下一步；一个里程碑通过后再进入下一个。
